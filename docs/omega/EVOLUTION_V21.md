# v21 — Stage 3 Performance Regression Gate

First new maintainer roadmap item. `omega_x_evolution.engine.Cascade` is the actual MultiStageEvaluationCascade implementation in the canonical repository. Its existing Stage 0 AST, Stage 1 smoke, Stage 2 property and Stage 3 deterministic quality/operation-proxy evaluation are unchanged. The coordinator extends Stage 3 with a measured regression gate (Stage 3b) **before audit, archive admission, routing rewards and positive training records**. `omega_x_evolution.performance` encapsulates measurement and decision policy. Remote results still undergo the existing independent recomputation, and no worker-supplied timing is trusted.

## Policy

For each successful Stage 3 candidate, compare with the actual accepted parent and the highest fixed-score elite in its target MAP-Elites cell; when the cell is empty compare with the current global archive champion. Duplicate reference source is measured once. References can change only through normal accepted archive evolution. Use the same fixed 96-point grid for correctness and timing, never the holdout. Baseline correctness is the accepted artifact's original quality on that same grid (all mandatory properties already passed); no new correctness objective replaces the existing metric. Historical baseline source is remeasured alongside the candidate, not compared to stale raw timings. Each record includes the candidate and baseline SHA-256, baseline ID, role, original operation proxy (`parent_performance`), quality, profiles, `parent_latency_ms`, and gate decisions. The latency milliseconds field is the median of per-round p50 individual-call latencies, not aggregate grid duration.

Warm up both validated AST interpreters on the grid. Three paired rounds, each with two passes over all 96 identical points; 192 individual latency samples per interpreter per round (576 per interpreter per baseline). Alternate AB/BA ordering, using `perf_counter_ns`. p50 is median, p95 and p99 nearest-rank empirical quantiles. The measured region is only `Expression.evaluate`, not parsing, oracle calculation, networking or sleep. Profiling occurs serially in the coordinator after the batch returns; a process-local lock serializes concurrent profiler calls. This is bounded CPU microbenchmarking, not a system-wide load test or guaranteed statistically significant inference. For each percentile compute the median of the three paired candidate/reference ratios minus one; use the maximum of these relative slowdowns. A single outlier round cannot by itself determine a percentile ratio. Shared-machine noise, clock resolution, CPU frequency and scheduling remain relevant. No hard realtime guarantee.

Default operator-controlled `Policy`: tolerance 0.05 relative latency, minimum correctness gain 0.02 absolute (2 percentage points), proportional gain coefficient 0.4, hard relative slowdown cap 0.25. If worst slowdown is <=5%, accept the latency gate. Above 5%, require gain >= max(0.02, 0.4 * slowdown); above 25%, reject regardless of gain. The last two parameters are additional conservative engineering decisions, configurable in the Python Policy API. Both distinct baseline comparisons must pass. A measurement/validation failure rejects the candidate. This fixes the supplied sketch's absolute subtraction of a normalized score and missing actual correctness check. `parent_performance` remains the **deterministic operation proxy**, not a latency measurement. The objective weights and safety invariants are unchanged, and passing the latency gate alone is not a promotion guarantee. The initial simple seed is not gated against itself. No false claim of automatic runtime reduction: the reported actual default run rejects 12/12 proposals, showing that strict latency constraints may stall the existing mutation operator.

## Activation and persistence

```sh
python -m omega_x_evolution --seed 5 --generations 3 --islands 2 --workers 2 --performance-regression
# With a private pre-existing 32+ byte random HMAC key:
python -m omega_x_evolution --seed 5 --generations 2 --islands 2 --workers 2 --performance-regression --checkpoint run.db --checkpoint-key-file run.key
python -m omega_x_evolution --seed 5 --generations 3 --islands 2 --workers 2 --performance-regression --checkpoint run.db --checkpoint-key-file run.key --resume
```

API: `await engine.run(cfg, performance_policy=performance.Policy())`; use `evaluation_processes=N` for trusted local process pool. `run_remote(..., performance_policy=Policy())` uses the same coordinator gate; `omega-x-distributed controller --performance-regression` activates it. Without opt-in the deterministic experiment path is retained, including v20 campaign scheduler and historical benchmark APIs. Timing evidence is included in the JSON report; with a checkpoint, it is committed atomically with the accepted archive and other generation state, under existing HMAC/CAS protection. The checkpoint contract binds policy, workload digest, source hashes, Python, OS, CPU description, affinity and clock resolution. Resume cannot omit the gate or change policy/context. Completed generation decisions and profiles are preserved, while uncommitted work may be remeasured and differ on resume. No deterministic equivalence for fresh measured runs, no cross-host baseline reuse, no anti-rollback guarantee. At most 1024 attempted candidates per measured campaign (bounded by the proposal count/credit budget), at most two reference profiles per Stage 3 candidate. Existing deterministic CLI behavior remains default deliberately to avoid silently turning reproducible experiments into timing-dependent ones.

**Compatibility boundary:** `engine.py` changed, so old exact-runtime-hash checkpoints (including old v9/v10/v20 contracts) intentionally do not resume under v21. Continue those with their matching archived release. No bypass or automatic migration of authenticated checkpoints is introduced. New v21 checkpoints resume under matching source/host-policy contracts. The v20 release archive remains available.

## Evidence

[Actual measured run](performance-benchmark-v21.json), seed 5, 3 generations, 2 islands, 2 workers. All 12 successful deterministic Stage 3 evaluations were rejected at measured Stage 3b. No claimed evolutionary improvement from this run. Unit and integration tests use deterministic synthetic profiles to prove exact threshold, correctness exception, percentile tail regressions, noise resistance, reference choice/veto, fail-closed profiling, durable history, local process execution and loopback remote coordination. Simulated profiles are not physical latency evidence. A real paired-profile test validates sample counts and percentile ordering. [Verification](verification-v21.txt).
